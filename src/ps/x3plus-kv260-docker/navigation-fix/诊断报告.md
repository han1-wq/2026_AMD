# 小车导航启动定位检查

已只读检查 KV260（192.168.43.182）启动脚本、容器内导航配置、旧运行日志，以及电脑端上位机与 RViz 启动脚本。未修改实车文件，未启动实车导航，未向实车发布目标或速度。检查时实车 ROS 节点列表只有 /rosout。

## 已确认的缺陷

1. `container/opt/x3plus_ws/src/yahboomcar_nav/rviz/yahboomcar_navigate.rviz` 包含两个 SetInitialPose 工具。第一个发布 `/start_point`，第二个发布 `/initialpose`；AMCL 接收后者。本机 `x3plus:melodic-amd64` 镜像也存在相同配置。选择前者不能为 AMCL 设置初始位姿。
2. `container/opt/x3plus_ws/src/yahboomcar_nav/launch/library/amcl.launch` 将 initial_pose_x/y/a 默认设置为 0，顶层启动文件未提供选择实际初始位姿的参数。完整重启会覆盖 AMCL 保存到参数服务器的上次估计；同时 `start-navigation.sh` 对同地图的健康实例直接复用，两条路径定位行为不同。
3. `start-navigation.sh` 第 102 行附近只检查节点、地图发布者与 map→odom 的存在，然后报告导航就绪；没有初始位姿确认、激光与地图一致性或定位质量检查。
4. `/home/amd/x3plus-kv260-docker/pc-console/console_backend.py` 的 probe_ok 只检查地图、激光和 TF，不要求收到 AMCL 位姿。`probe-ros.py` 虽订阅定位，只记录消息数量，不记录位姿或协方差。
5. `send_mark.py` 收到 `/clicked_point` 后会立即发布第一个目标，无初始定位门槛；成功后循环导航，失败时自动重试。move_base 配置启用旋转恢复；旧日志存在 DWA 失败、旋转恢复与碰撞拒绝记录。不能据此断言旧现场一定发生旋转运动。

## 隔离仿真

本机 Docker `--network none`，无设备映射，内存上限 768 MiB、2 CPU。使用真实 AMCL（ROS Melodic 1.16.7），加载从实车复制的 AMCL launch；合成非对称二维地图、射线激光以及 odom→base→laser TF。未启动底盘驱动或 move_base。通过 request_nomotion_update 获得静止条件下的多次观测；这不是 Gazebo 动力学仿真或实车传感器回放。

合成真实位姿：(2.0 m, 1.0 m, 0.6 rad)。里程计位姿故意设为 (4.0 m, -2.0 m, 1.0 rad)，验证 map 位姿不应简单等同于里程计零点。

| 场景 | AMCL 估计 x/y（m） | 位置误差 | map→odom |
| --- | --- | --- | --- |
| 默认零位姿冷启动 | 0.152 / 0.256 | 1.992 m | 存在 |
| 向 /start_point 发布真实初始位姿 | 0.157 / 0.357 | 1.952 m | 存在 |
| 向 /initialpose 发布相同初始位姿 | 1.934 / 0.988 | 0.067 m | 存在 |
| 完整重启 AMCL | 0.003 / 0.001 | 2.233 m | 存在 |

仿真退出码 0，断言标记 `AMCL_REPRODUCTION_PASS`。原始值在 amcl-results.json，脚本为 simulate_amcl.py。单次粒子滤波数值有随机性，不能当作实车精度指标。正确初始化时有一次轻微 TF 时间外推警告，随后收到了 16 条定位消息，最终误差小于脚本 0.3 m 阈值。

重启后错误估计的 x/y 方差约为 0.0111 / 0.00094 m²，说明小协方差也可能对应错误匹配，不能单独作为放行导航的依据。

## 其他配置问题

电脑 `start-pc-rviz.sh` 调用 `view_navigate.launch`，但当前本机 `x3plus:melodic-amd64` 镜像缺少此文件。这是另一处可复现的启动配置不一致；本次没有启动图形界面，不能确定用户看到的问题是否来自这个镜像/入口。RViz 配置文件本身存在。应区分“启动导航服务”和“打开导航 RViz”：电脑上位机按钮只做后者。

旧实车日志曾出现地图更新周期约 1～5.25 s，而配置要求 10 Hz；规划器也配置为 10 Hz。该记录证明曾有严重实时性不足，原因可能涉及负载或等待，应进一步采样 CPU、扫描和 TF 延迟，不能直接归因于内存。

## 推荐修复顺序

1. 导航 RViz 保留唯一的 AMCL 初始位姿工具，话题固定 `/initialpose`；清楚命名目标工具，避免 `/transport/goal` 等其他流程混淆；修正电脑镜像缺少的启动入口。
2. 将服务启动状态改为“等待定位确认”；按地图选择人工初始位姿或经过校验的固定停靠位姿。明确冷启动和同地图复用策略，不把启动动作解释为回到地图原点。地图 YAML 的 origin 是地图栅格原点，也不等于小车当前位置。
3. 在所有目标入口和底盘速度输出链路增加板端统一放行条件：本次定位确认、新鲜有效的 scan/TF、可接受的位姿变化与协方差、激光与地图匹配。失效时撤销目标并关闭输出放行。只在 UI 禁用按钮无法覆盖 RViz、action 和多点导航入口。
4. 定位未确认时不运行导航恢复动作；将单点导航和持续巡航明确分开，并设置可观察的取消状态。
5. 在上述行为通过隔离回归后，再以现场 scan/odom/TF 录制数据进行回放验证，检查外参、扫描方向和真实地图匹配。实车行驶验收仍未进行。

本次结论是多个已证实的软件缺陷可以造成或放大该现象，尚不能仅凭历史日志确定用户每一次异常具体触发了哪条路径。
