## 原因与证据

1. 前次现场观测的门控状态为 `ready=false / high_pose_uncertainty_initial_pose_required`，输出 `/cmd_vel` 为零。采样时位置标准差约 4 cm、yaw 标准差约 0.27°，小于默认 35 cm、约 17.2° 门槛。这些历史观测说明定位确认已被早先事件撤销，不能证明当时传感器一直健康。
2. 原 `navigation_guard.py` 的 `tick()` 遇到任何质量检查失败都会调用 `invalidate()`，清除 `initial`。此后 `check()` 遇到 `initial is None` 直接返回历史原因，数据恢复也不能重新放行。一次短暂协方差或时间戳异常即可永久锁定，目标被拒绝或取消，车不会执行位置或朝向。
3. 原 `start-navigation.sh` 即使复用同地图健康实例，也主动调用 `/navigation_guard/reset` 撤销定位。这是另一条要求重设位姿的路径；电脑“启动导航 RViz”本身只打开查看器，不调用板端启动脚本，因此不能把这条路径归因于每一次 RViz 点击。
4. 当前 RViz `2D Pose Estimate` 发布 `/initialpose`，`2D Nav Goal` 发布 `/move_base_simple/goal`，目标四元数被完整转发。真实 AMCL + move_base 隔离测试验证目标位置、不同终点朝向和仅旋转目标能执行；没有证据把本次已观察到的完全不动归因为箭头方向被丢弃。

尚不能确认的部分：断线前是否还存在过期扫描、时钟不同步、规划失败、底盘订阅或串口驱动问题。历史日志存在控制/代价地图更新耗时过长，不能据此确定当前硬件根因。

## 新行为

| 事件 | 行为 |
| --- | --- |
| 冷启动、换图、定位跳变、AMCL 序列重启、人工 reset | 归零、撤销目标，需新初始位姿 |
| 短暂协方差超限、scan/AMCL/TF 过期、地图匹配失败 | 立即归零、撤销目标，暂留已确认会话 |
| 首次异常起 5 秒内恢复，并连续健康 2 秒 | 恢复接收新目标；无需重复初始位姿；旧目标和旧速度不续跑 |
| 5 秒内不能完成稳定恢复，包括反复抖动 | 锁定，需人工核对并重新初始化 |
| 同一地图健康实例复用 | 调用新 `/navigation_guard/stop`，撤销旧目标但保留定位状态 |

`~stable_seconds=2`，新增 `~transient_timeout=5`；要求 `0 < stable_seconds < transient_timeout`，5 秒包含恢复验证时间。原有传感器时效、协方差、初始位姿一致性、激光匹配和射线冲突门槛均保留。恢复期间仍比较 map→odom 修正变化，防止“恢复”掩盖定位跳变。初始定位尚未确认时，不进行自动确认绕过。

目标执行与速度输出绑定定位 epoch。停止后即使规划器还有迟到速度，或取消与成功结果竞态，也不能把旧目标当成功继续放行。stop 服务同样拒绝其之前的目标时间戳。恢复只允许接收恢复后新发送的目标。

`/navigation/localization_status` 新增 `current_fault`、`initial_pose_required`、`latched_reason`、`recovery_remaining_s`。历史锁定与当前数据健康分别报告。控制台显示中文原因；书签按钮置于状态框上方，短窗口可见。

```bash

docker exec x3plus-robot bash -c 'source /opt/ros/melodic/setup.bash; rosnode list'

cd /home/ubuntu/x3plus-kv260-docker

  -T navigation-fix/recovery-install/navigation-fix/recovery-deployment-files.txt
cp -a navigation-fix/recovery-install/. /home/ubuntu/x3plus-kv260-docker/

python3 /home/ubuntu/x3plus-kv260-docker/navigation-fix/sync-runtime.py --container x3plus-robot --check
```

首次运行备份命令时，新文件不存在的告警可忽略；其他权限、磁盘和校验错误须处理。`sync-runtime.py` 在运行文件不一致且有活动节点时拒绝安装；已有容器文件会另存时间戳备份。安装不启动运动。不要只更新电脑 UI，板端旧门控不会获得新的恢复行为。

启动现有硬件与同一保存地图的导航服务后：

1. 重开电脑控制台、打开导航 RViz。对照实车和激光地图设置一次 `2D Pose Estimate`，等待 ready。箭头起点是车在地图上的实际位置，方向是车头。
2. 在可通行空地发短距离 `2D Nav Goal`，其箭头起点是目标位置，方向是到点后的车头朝向。观察公开 action 结果；到达第一个目标后直接发第二个不同朝向目标，不重复 estimate。
3. 若不动，在控制台点“检查实际数据与 TF”，保存完整 JSON。探针采集 `/move_base/status`、`/navigation_internal/move_base/status`、`/cmd_vel`、`/navigation_internal/cmd_vel` 和扫描年龄，且仅订阅。
4. `ready=false`：按 `current_fault` 排查扫描时间戳、TF、协方差或匹配；`initial_pose_required=true` 才表示需要人工重新初始化。短暂恢复后旧目标已取消，要重新发新目标。
5. `ready=true` 但内部 action 拒绝/中止：查路径、目标是否可达、代价地图和 move_base 日志。内部速度非零而公开速度为零：查门控和 action 活动状态。公开速度非零但不动：查 `/cmd_vel` 底盘订阅、驱动节点、串口与电源。
6. 若 scan 长期过期，检查雷达节点、两端时钟、网络和 CPU/控制周期延迟；不要靠取消时效检查来放行。对实车到点与转向分别测量误差。
