## 行为变化

1. 导航 RViz 只保留一个 `2D Pose Estimate`，固定发布 `/initialpose`；只保留 `/move_base_simple/goal` 导航目标工具。电脑和板端查看器都加载宿主机挂载的修复配置，不依赖旧镜像缺少的导航 launch。
2. 服务启动与定位确认分开。冷启动使用 AMCL 的确定性种子，清理旧 AMCL 私有参数，不自动信任上次位姿。同地图复用时调用 `/navigation_guard/reset`，撤销定位确认并取消目标。默认种子 `(0,0,0)` 不代表真实位置，也不会自动放行。
3. 板端 `navigation_guard.py` 承接公开 `/move_base` action 和 RViz 单点入口，规划器 action/速度放在 `/navigation_internal`。未确认定位时拒绝目标，规划速度只能经过门控输出。`navigation_internal` 是内部连接约定，不是 ROS1 网络权限隔离；本改动不阻止其他进程直接向 `/cmd_vel` 发布。
4. 放行要求：本次有效 `/initialpose`、更新后的 AMCL 位姿、初始位姿一致性、合理协方差、有效且新鲜的激光和 TF、连续约 2 秒的激光终点与地图障碍一致性。位姿显著跳变、AMCL 序列重启、地图变化、数据失效会关闭放行、取消目标并要求重新初始化。旧会话目标不能在重新确认后继续执行。
5. 默认关闭多点导航；显式启用时也受门控限制，取消原来的自动重试和无限循环。当前 AMCL 导航路径关闭自动恢复行为与旋转恢复；其他导航模式的共享 move_base 默认配置没有改成门控模式。
6. 导航命令超过约 0.3 秒未更新会输出零速度；X3plus 驱动增加约 0.5 秒速度命令超时归零，并拒绝 NaN/Inf。软件停车不能证明电机实际制动，也不能覆盖驱动进程或串口本身失效。
7. 电脑诊断分开显示数据连通与定位确认。必须收到新鲜 AMCL 位姿和板端状态才确认导航；仅有地图、激光和 TF 不再被解释为定位确认。
8. `run-robot.sh` 校验并在空闲容器中安装修复文件，`start-navigation.sh` 启动前核对运行文件校验和。发现活动节点且文件不一致时拒绝覆盖，防止重建容器后静默回退到旧实现。

## 默认门槛

| 检查 | 默认值 |
| --- | --- |
| 激光、里程计 TF 最大年龄 | 0.7 s |
| AMCL 位姿最大年龄 | 3 s；每约 0.5 s 请求静止更新 |
| AMCL 平面位置最大标准差 | 0.35 m，检查 xy 协方差特征值 |
| AMCL 航向最大标准差 | 0.30 rad |
| 初次收敛与所设位姿允许差 | 0.5 m / 0.5 rad |
| 激光终点邻近障碍距离 | 0.20 m |
| 激光匹配比例 | 至少 65%，至少 30 条有效返回，采样约 120 条射线 |
| 连续通过时间 | 2 s |

这些是导航放行门槛，不是实车精度承诺。匹配门槛应结合现场动态障碍、可见墙面和雷达数据验证；重复或对称环境仍可能错误匹配。固定地图需预先存在，不会自动判断“车当前恰好位于地图原点”。

## 现在的操作流程

1. 在安全场地按现有流程启动底盘与雷达，再选择正确地图启动导航服务。
2. 打开导航 RViz，在地图上实际车的位置拖出 `2D Pose Estimate`，箭头方向对应车头。不要把地图 origin、odom 零点或屏幕中心当作实际车位。
3. 等待板端 `/navigation/ready` 为 `true`，并确认 RViz 激光与实际墙面轮廓重合。可在电脑上位机执行实测检查，查看板端定位确认状态。
4. 放行后重新下发 `2D Nav Goal`。放行前的目标不会排队等待执行。
5. 若定位失效并停止，需要检查数据、重新设置初始位姿并发送新目标。仅恢复激光或再次打开 RViz 不会自动续跑。

板端只读查询示例：

```bash
docker exec x3plus-robot bash -c 'source /opt/ros/melodic/setup.bash; rostopic echo -n 1 /navigation/localization_status'
```
